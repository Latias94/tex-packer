# Releasing tex-packer

tex-packer has two independent release channels:

- `.github/workflows/release.yml` is generated by `dist`, then hardened by
  `tools/update_dist_workflow.py`. A pushed version tag builds CLI archives and
  installers for macOS, Linux, and Windows, then creates the GitHub Release.
- `.github/workflows/release-crates.yml` is manually dispatched. It publishes
  `tex-packer-core`, `tex-packer-cli`, and `tex-packer-gui` to crates.io in
  dependency order.

Both channels call `.github/workflows/release-tag-check.yml`, so neither can
publish unless the source is an annotated `vX.Y.Z` tag (including the supported
`alpha.N`, `beta.N`, and `rc.N` prerelease suffixes).

The GUI crate remains available through crates.io but is intentionally excluded
from prebuilt `dist` artifacts until it has a cross-platform GUI test matrix.

## One-time crates.io setup

Configure a trusted publisher for each of the three crates in crates.io:

- GitHub owner: `Latias94`
- GitHub repository: `tex-packer`
- Workflow filename: `release-crates.yml`
- GitHub Environment: `crates.io`

Create the `crates.io` Environment in the GitHub repository and restrict its
deployment branches to `main`. This restriction is mandatory: GitHub lets a
maintainer dispatch a workflow from another ref, while the trusted publisher
identity is scoped to the workflow and Environment. Add required reviewers when
the repository has an independent release approver.

The workflow exchanges GitHub's OIDC identity for a short-lived crates.io token;
do not add a long-lived `CARGO_REGISTRY_TOKEN` repository secret. Repository code
is tested and packaged before the OIDC-enabled job starts. The credentialed job
only uploads with `--no-verify` and checks the immutable crates.io checksum.

## Release procedure

1. Update all three package versions together and finalize `CHANGELOG.md`.
2. Run the workspace release gates documented in the root README.
3. Commit the release, create an annotated `vX.Y.Z` tag, and push both the
   default branch and the tag.
4. Confirm the generated `Release` workflow produces the expected CLI artifacts
   and GitHub Release.
5. From the `main` workflow ref, manually run `Publish crates.io` with the same
   tag. Approve the `crates.io` Environment deployment when required.
6. Install the published CLI from crates.io and run `tex-packer --version` plus
   a representative packing command.

The crates workflow checks out the tag, verifies its commit and all package
versions, runs the release gates, and records the SHA-256 of each packaged crate
before requesting an OIDC token. It skips an existing version only when the
registry checksum matches that package, so rerunning the same tag can continue
after a partial publication without accepting a foreign artifact. A crates.io
publication is permanent; do not move or recreate a release tag after
publication.

## Updating dist

Install the `dist` version declared in `dist-workspace.toml`. Use the repository
wrapper to regenerate the workflow; it applies the least-privilege patch that
keeps write access out of artifact build jobs:

```text
python tools/update_dist_workflow.py
python tools/update_dist_workflow.py --check
dist plan --allow-dirty --tag vX.Y.Z
actionlint .github/workflows/release.yml .github/workflows/release-crates.yml .github/workflows/release-tag-check.yml
```

Do not edit `.github/workflows/release.yml` directly. Change
`dist-workspace.toml` or the hardening function in the wrapper, regenerate, and
review the resulting diff. Put crates.io-specific behavior in
`release-crates.yml`.
